# Security policy

## Reporting a vulnerability

Email **<contact@creavisiontechnology.com>** with `SECURITY` in the subject.
Please do **not** open a public issue for a vulnerability.

Tell us what you can: what the problem is, how to reproduce it, which version
(`creabus-tool --version`), and what you think an attacker could achieve. A
proof of concept helps a great deal; so does a guess at severity, even a rough
one.

| | |
| --- | --- |
| We acknowledge receipt within | 5 working days |
| We give you an initial assessment within | 15 working days |
| We aim to release a fix within | 90 days of the report |
| Credit | Your name in the changelog and the advisory, unless you prefer otherwise |

If a fix will take longer than 90 days we will tell you why and agree a date
with you. If you tell us you intend to publish on a particular date, we will
work to it.

## What is in scope

Anything in this repository that ships in a release: the protocol code, the
transports, the profile loader and its expression language, the window, and
the build workflow.

Out of scope, because they are not defects:

* **A device profile that does something you did not expect.** A profile is
  input, and its expression language is deliberately limited (see below) — but
  if you find a way *past* that limit, that is very much in scope and we want
  to hear about it.
* **Binding to `0.0.0.0`.** That is the documented default for a simulator and
  is what makes it reachable from the machine under test. Bind to a specific
  interface if you do not want that.
* **The simulator answering anybody who connects.** Modbus has no
  authentication. Neither does this.

## What this software does and does not protect

Being honest about the model is more useful than a list of features.

**Modbus has no security at all.** No authentication, no encryption, no
integrity beyond a CRC that catches noise rather than tampering. Anyone who
can reach the port can read every register, and can write every writable one.
This is a property of the protocol, not of this implementation, and no version
of this tool can fix it. Keep Modbus on a segregated network. If it has to
cross an untrusted one, put it inside a VPN or a TLS tunnel.

**Treat the tool as having the reach of whoever runs it.** It writes to
whatever device answers at the address it is given.

**Device profiles are input, and are treated as hostile.** A profile can
compute one register from others, which means a profile file carries code.
That code is parsed and checked against an allowlist of syntax before anything
runs: no attribute access, no indexing, no lambdas, no comprehensions, no
imports, no calls except to a fixed list of maths functions. A profile that
steps outside it is refused when it loads, not sandboxed while it runs. See
[`creabus_tool/expressions.py`](creabus_tool/expressions.py), which documents
the escape this is built to stop, and `tools/selftest.py`, which tries that
escape and thirteen others on every CI run.

**Network input is treated as hostile.** Frames arriving from a peer are
length checked and bounds checked before they are decoded; the RTU framer caps
what it will buffer; the TCP server caps concurrent clients; a read of a
register that does not exist is answered with an exception rather than
whatever is next in memory.

**What we do not claim.** This is a desktop engineering tool, not a security
product. It has had no third party penetration test and no formal
certification. It does not sandbox itself from the operating system, and it is
not hardened against a hostile local user who already has your account.

## Supported versions

While the leading version number is 0, only the latest release gets fixes.
That will change when 1.0 is released.

## Software bill of materials

An SBOM in CycloneDX format is generated by `tools/sbom.py` and published with
every release as `sbom.cdx.json`. It lists every component that ends up inside
a release binary, with versions and licences.

```bash
python tools/sbom.py            # writes sbom.cdx.json
```
